## الخلاصة في 6 نقط

1. **Drive اتغيّر كتير بعد آخر import في 9 نوفمبر.**
   - كان فيه 133 صورة، دلوقتي **236 صورة** (حوالي **399 MB**).
   - منهم **65 صورة جديدة**: **7 أوض نوم** جديدة، و**6 أوض أطفال**، و21 صورة ركن وأنتريه.
2. **يوم 19 نوفمبر المالك عمل re-upload لمعظم الفولدرات.**
   - الفولدرات القديمة راحت الـ Trash، ونفس الصور اترفعت تاني بـ **file IDs جديدة**.
   - اتأكدت إن الملفات متطابقة بالاسم والحجم، وعملت تحقق بالـ SHA-256 على عيّنة واحدة وطلعت متطابقة.
   - **الدرس:** الـ sync لازم يعتمد على **كود المنتج + content hash**، مش على Drive IDs، لأن الـ IDs بتتغيّر لما المالك يعيد التنظيم.
3. **الموقع الـ live فيه 48 منتج في 7 أقسام.**
   - كل صوره معمولة من Drive قبل كده، وكل صورة مسجّل جنبها مصدرها في Drive والـ SHA-256 بتاعها.
   - **5 منتجات** بتستخدم صور مصدرها اتمسح من Drive. المنتجات دي لسه شغالة لأن الصور متخزنة في الموقع نفسه.
4. **Drive نفسه مفيهوش أي بيانات منتجات**: لا أسماء ولا مقاسات ولا خامات، صور بس.
   - الأسماء والأوصاف اللي على الموقع اتكتبت من وصف الصور، والمنتجات متعلّمة `illustrative`.
   - كل الصور renders معمولة بالـ AI (أسماء ملفات زي "ChatGPT Image…").
5. **أكبر مشكلة للأتمتة: فولدرات الركن والأنتريه مسطّحة (flat).**
   - كل الصور مرمية في فولدر واحد، ومفيش أي طريقة تعرف منها أنهي صور بتاعة نفس المنتج.
   - في أوض النوم والأطفال كل room ليه فولدر لوحده، وده الشكل الصح.
6. **التوصية:**
   - Google Drive للصور + **Google Sheet واحد** للبيانات.
   - **GitHub Actions** تشتغل كل 15 دقيقة: تعمل sync، وتجهّز الصور، وتعمل build و deploy على نفس الـ Cloudflare Worker الحالي.
   - الصور المتجهّزة والنسخ الأصلية الاحتياطية تتخزن في **Cloudflare R2**.
   - **التكلفة المتوقعة $0 في الشهر**، والتحديث بيوصل للموقع في حوالي **15–30 دقيقة**.

## 4) هيكل Drive المقترح

عملته على شكل أوض النوم الحالي، لأنه بالفعل الأنسب: **فولدر لكل منتج، وجوّاه صوره بس**.

```
الكتالوج/
├── 📊 بيانات الكتالوج            ← Google Sheet (الأسماء والمقاسات والحالة)
├── 1 غرف نوم/
│   ├── BR-05 بيج بألواح خشب/      ← كود ثابت + اسم وصفي بالعربي (حر)
│   │   ├── 01.jpg                ← الصورة اللي اسمها يبدأ بـ 01 = الرئيسية
│   │   ├── 02.jpg  03.jpg …      ← صور التفاصيل بالترتيب
│   └── BR-13 …/
├── 2 غرف ملابس/     DG-…
├── 3 غرف أطفال/     KB-…
├── 4 أنتريهات/      LR-…
├── 5 ركن/           CO-…
├── 6 نيش/           CC-…
├── 7 سفرة/          DR-…
└── _أرشيف/          ← نقل فولدر منتج هنا = يتشال من الموقع (وبيرجع لو رجعته)
```

**القواعد:**
- **كود المنتج** (`BR-13`) في أول اسم الفولدر هو الهوية الثابتة.
  - نغيّر اسم الفولدر أو نعيد رفعه أو ننقله، ويفضل نفس المنتج ونفس الـ URL.
  - المنتجات الحالية بتاخد نفس أكوادها: `PV-BR-05` تبقى `BR-05`، وداخلياً تفضل `pv-br-05`، فمفيش URL يتغيّر.
- **فولدر القسم بيحدد القسم الافتراضي**، والـ Sheet يقدر يغيّره.
- **الصورة الرئيسية:** أول ملف اسمه يبدأ بـ `01`. لو مفيش، أول ملف بالترتيب الأبجدي.
- **البوسترات اللي فيها نص عربي أو إنجليزي** (لو اتقرر نستخدمها): نضيف للاسم `-ar` أو `-en` عشان كل لغة تتعرض صورتها بس.
- **الصور الأصلية ما تتغيّرش أبداً.** الـ sync بيقرأ بس، وأي إعادة تنظيم بتحصل بعد موافقتك وعن طريق المالك.

## 6) مقارنة الـ architectures

القيود اللي حكمت المقارنة:
- الموقع SSG على Workers **Free**.
- الـ rendering وقت الطلب خطر على الـ CPU limit (10 ms).
- عشان كده الأنسب إن الكتالوج **يتبني وقت الـ build**.

| المعيار | ① Drive API + GitHub Actions | ② Drive API + Worker (runtime) | ③ Drive + R2 (تخزين بس) | ④ سيرفر sync مستقل | ⑤ Apps Script |
|---|---|---|---|---|---|
| تعقيد الإعداد | متوسط | عالي: محتاج ISR + queue + incremental cache | لوحده مش حل. هو مكوّن في ① | متوسط | قليل |
| التكلفة الشهرية | **$0** (public repo) | $0، لكن الأرجح هيحتاج Workers Paid (‎$5) عشان الـ CPU | ‏$0 لحد 10 GB | ‏‎$4–6 VPS | ‏$0 |
| الاعتمادية | عالية: نفس الـ build والـ guards الحالية | أقل: SSR على Free ضرب الـ CPU قبل كده | — | حسب صيانة السيرفر | تشغيل محدود |
| التأخير | ~15–30 دقيقة | دقايق | — | دقايق | ~5–10 دقايق كـ trigger بس |
| أداء الصور | ممتاز: renditions جاهزة على CDN | ممتاز | ممتاز (zero egress) | حسب الاستضافة | — |
| الأمان | service account read-only + secrets في GitHub | نفس الشيء، والـ secrets في Worker | — | سيرفر مفتوح محتاج patching | التوكن جوّه script في حساب المالك |
| الـ Scalability | مئات المنتجات بسهولة | جيدة | جيدة | جيدة | ضعيفة |
| الـ Quotas | Drive: ‏325,000 unit/min لكل user (زيادة جداً) | Drive نفسه، + 50 subrequest/invocation على Free | ‏1M Class A و10M Class B في الشهر | — | ‏90 دقيقة triggers/يوم، و20k UrlFetch/يوم |
| الصيانة | قليلة | أعلى | قليلة | عالية | متوسطة |
| التوافق مع الحالي | **كامل**: نفس `cf:deploy:production` | محتاج إعادة تصميم الـ rendering | مكمّل | غريب عن الـ stack | ما ينفعش يعمل image optimization ولا deploy |

**المصادر:** صفحات R2 pricing، وWorkers limits، وImages pricing، وGitHub Actions billing وschedule، وDrive API quotas، وApps Script quotas. كلها اتقرت النهارده.

**ليه مش Drive links مباشرة على الموقع؟**
- الفولدر **مش public**.
- Drive مش CDN: مفيش image optimization ولا caching مضمون.
- الروابط بتقع لما الملفات تتعمل لها re-upload، **وده حصل فعلاً يوم 19 نوفمبر**.

**ليه مش GitHub للصور؟**
- الـ repo بيكبر مع كل صورة جديدة.
- والـ repo public كمان.

## 7) الـ architecture المقترح

```
Google Drive (صور) + Google Sheet (بيانات)
        │  read-only service account (drive.readonly)
        ▼
GitHub Actions — schedule كل 15 دقيقة + زرار "Run" يدوي
  1. list الفولدر كله + قراءة الـ Sheet
  2. validate: listing كامل؟ مفيش API error؟ (أي فشل = وقف، والموقع يفضل زي ما هو)
  3. diff ضد آخر manifest (بالكود + md5Checksum من Drive)
  4. الصور الجديدة/المتغيرة بس: download ← sharp ← WebP/AVIF 640 و1400 (من غير upscale)
  5. upload للـ R2 بأسماء content-addressed (hash) + نسخة احتياطية من الأصل
  6. توليد catalog JSON ← commit للـ repo (سجل كامل + rollback بـ git revert)
  7. npm run cf:deploy:production (نفس الـ guards الحالية) ← smoke test
  8. كتابة نتيجة كل منتج في عمود "حالة المزامنة" في الـ Sheet
        ▼
Cloudflare Worker (نفس الموقع) + R2 public custom domain للصور (media.alnasrfurniture.com)
```

**ليه ده الأنسب:**
- بيحافظ على **الـ static prerender والـ cache** اللي خلّوا الموقع سريع وفي حدود Workers Free.
- بيستخدم **نفس سكربت الـ deploy** ونفس الـ guards اللي اتجربت.
- بيضيف R2 بس، ومفيش database ولا سيرفر.

**ضمانات الحذف والسلامة:**
- **الـ sync ما بيمسحش حاجة لو حصل أي من دول:** أي API error، أو listing ناقص، أو مشكلة صلاحيات، أو عدد المنتجات المتشالة أكبر من حد معين (مثلاً أكتر من 3 أو أكتر من 10% في مرة واحدة). في الحالة دي بيوقف ويكتب تنبيه في الـ Sheet.
- **الحذف بيحتاج تأكيد مزدوج:** المنتج يتشال بس لما يختفي في **مزامنتين ناجحتين ورا بعض**.
- **الحذف بيعمل archive، مش مسح نهائي:**
  - الـ URL بيعمل redirect للقسم أو بيفضل شغال، حسب السلوك الحالي.
  - صوره بتفضل في R2 لمدة 90 يوم.
- **رفع ناقص:** أي فولدر اتعدّل في آخر **10 دقايق** بنستنّاه، عشان ما ننشرش منتج والمالك لسه بيرفع صوره.
- **Idempotency:** المفتاح هو الكود + hash الصورة. تشغيل الـ sync مرتين بيطلّع نفس النتيجة، ومن غير duplicates. والصورة المكررة بالبايت بتتعرض مرة واحدة.
- **Recovery:** فيه 4 طبقات:
  1. Drive Trash لمدة 30 يوم.
  2. نسخة الأصل في R2.
  3. `git revert` للـ catalog JSON.
  4. `wrangler rollback` لنسخة الـ Worker اللي قبلها، وده اتجرّب فعلاً في الـ staging.

**مدة التحديث المتوقعة:**
- من ما المالك يرفع لحد ما يظهر على الموقع: حوالي **15–30 دقيقة**.
- الـ schedule كل 15 دقيقة، وGitHub بيقول إن التنفيذ ممكن يتأخر وقت الزحمة.
- الـ build والـ deploy **تقدير**: حوالي 5–10 دقايق، وما اتقاسوش على CI لسه.

## 8) التكلفة الشهرية المتوقعة

| البند | التكلفة | الأساس |
|---|---|---|
| GitHub Actions | $0 | "free for standard GitHub-hosted runners in public repositories" |
| Drive API / Sheets | $0 | quotas أعلى بكتير من الاستخدام المتوقع |
| Cloudflare R2 | $0 | ‏10 GB مجاناً. الأصول حالياً ~0.4 GB، والـ renditions ~0.1 GB |
| Workers | $0 | نفس الخطة الحالية |
| **الإجمالي** | **$0** | |

**تحذيرات:**
- **محتاج أتأكد:** Cloudflare ممكن يطلب **وسيلة دفع** عشان يفعّل R2 حتى على الـ Free. أي تغيير في الـ billing محتاج موافقتك.
  - **البديل لو رفضت:** الصور تتحط في static assets بتاعة الـ Worker. الحد 20,000 ملف لكل version، وده كفاية، بس الـ build هيبقى أبطأ.
- **خطر موجود دلوقتي ومالوش علاقة بالمشروع ده:**
  - الموقع بيستخدم `next/image` مع Cloudflare Images binding.
  - الـ Free plan فيه **5,000 unique transformation في الشهر**. لما تخلص، الصور الجديدة بترجع error 9422.
  - كل ما الكتالوج يكبر الخطر بيزيد.
  - **الحل في الـ pipeline الجديد:** نولّد الـ renditions بنفسنا ونقدّمها من غير transformation. محتاج قرار أثناء التنفيذ.

## 9) خطة التنفيذ (بعد موافقتك)

1. **إعداد** (حوالي نص يوم):
   - Google Cloud project و service account.
   - المالك يشارك الفولدر معاه كـ Viewer، والـ Sheet كـ Editor.
   - R2 bucket وcustom domain، ودي بعد ما الـ zone تبقى Active.
   - GitHub secrets.
2. **الـ Sheet والهيكل** (حوالي نص يوم): أجهّز الـ Sheet بالمنتجات الـ 48 الحالية وأكوادها، وأحط فيه **خطة نقل** لكل فولدر: من فين لفين. **المالك هو اللي ينقل**، أو يديني Editor.
3. **سكربت الـ sync** (حوالي يومين):
   - تطوير من `scripts/import-drive-catalog.ts` الموجود.
   - الـ manifest، والـ diff، والـ safety gates، والـ renditions، والـ catalog JSON، وكتابة الحالة في الـ Sheet.
4. **Workflow + staging أولاً** (حوالي يوم):
   - الـ sync يشتغل على الـ staging Worker الأول.
   - أختبر كل السيناريوهات المطلوبة في Phase 6: إضافة، وتعديل، واستبدال صورة، وحذف، ونقل بين أقسام، وملف مكرر، ورفع ناقص، وبيانات ناقصة، وفشل API، واسترجاع، وتشغيل متكرر.
   - وفوق ده Lighthouse في EN و AR، والـ SEO والـ redirects، والـ RFQ والواتساب.
5. **الـ migration الأولى** (حوالي يوم): الـ 13 room الجديدة تدخل بأسماء محايدة لحد ما المالك يكتب الأسماء الحقيقية، ومن غير أوصاف مؤلفة.
6. **دليل المالك** بالعامية: صفحة واحدة.
7. **Production:** بعد موافقتك، وبعد ما الدومين يتربط.

**المتطلبات المسبقة:**
- **merge الـ branch على `main`:** الـ scheduled workflows بتشتغل من الـ default branch بس.
- **الـ zone تبقى Active:** عشان الـ R2 custom domain.

## 10) الصلاحيات المطلوبة والقرارات الباقية

**صلاحيات:**
1. **المالك** (صاحب حساب Google اللي عنده الفولدر):
   - يشارك الفولدر كـ **Viewer** مع إيميل service account هنعمله.
   - يشارك الـ Sheet كـ **Editor**.
2. **Google Cloud project:** مجاني. هعمله بحسابك بعد موافقتك.
3. **Cloudflare API token** مقصور على Workers deploy وR2 للـ bucket ده بس، ويتحط كـ GitHub secret.
4. **إعادة تنظيم Drive:** إما المالك ينفّذ الخطة اللي هجهّزها، أو يديني Editor مؤقت.

**قرارات محتاجك:**
1. **النشر التلقائي من غير أسماء:**
   - **توصيتي:** الفولدر الجديد يتنشر لوحده باسم محايد، زي "طقم غرفة نوم BR-13"، لحد ما المالك يكتب الاسم.
   - **البديل:** المنتج يفضل مخفي لحد ما الاسم يتكتب.
2. **room 11 و room 13** (غرف نوم): منتج واحد ولا اتنين؟
3. **الملفات المسطّحة في الركن والأنتريه** (21 صورة جديدة): المالك يقسّمها في فولدرات منتجات، ولا كل صورة تبقى منتج لوحدها زي النظام الحالي؟
4. **الـ 40 بوستر القديمين** (فيهم نص ومقاسات): ننشرهم؟ نتجاهلهم؟ ولا نأرشفهم؟
5. **الـ 5 منتجات اللي مصدر صورهم اتمسح** (`pv-br-11`، `pv-lr-03`، `pv-co-01..03`): نخليهم زي ما هم، ولا نشيل الصور دي؟
6. **كل الصور AI renders:** هل عندكم صور حقيقية لمنتجات اتصنعت؟ لحد ما ده يحصل، علامة "تصميم توضيحي" لازم تفضل.
7. **R2 لو طلب وسيلة دفع:** نوافق، ولا نروح للبديل؟
